I go deep on the parts that decide whether a system survives: how it's structured, how the data moves, where it gets slow.

Then I own the whole product around that — frontend, mobile, deployment — because handing off half the thing is how good backends end up behind bad interfaces.

<br/>

### `01` &nbsp; Where I go deep

- **Architecture** — modular monoliths and microservices with boundaries that hold, so new features don't mean monolith-wide rewrites.
- **Data & performance** — SQL query plans, stored procedure tuning, Redis caching on sub-second hot paths, heavy aggregation moved off the transactional core.
- **Delivery** — CI/CD, containers, and getting it into users' hands without a second team.

<br/>

### `02` &nbsp; Selected work

▸ **Greenfield product** — architected a modular monolith from scratch as backend lead on a 3-person team; drew boundaries so any area could be extracted into its own service later without a rewrite. Shipped the mobile app to both stores — on a 3-person team, *"not my layer"* isn't an option.
<sub>`ASP.NET Core` · `PostgreSQL` · `Redis` · `Flutter` · `Docker`</sub>

▸ **Performance under load** — tuned SQL procedures, query plans, and Redis caching for sub-second hot paths on a large-scale platform; built a standalone reporting server that moved month-end aggregation off the transactional core.
<sub>`MS SQL` · `Redis` · `React` · `Microservices`</sub>

▸ **Platform extension** — improved module boundaries across reporting and integrations so changes ship with less regression risk; introduced MCP-assisted review and migration workflows that the team adopted.
<sub>`ASP.NET Core` · `MS SQL` · `MCP`</sub>

▸ **ERP delivery** — led backend delivery across manufacturing and hospitality rollouts, extending business areas without monolith-wide rewrites, with reporting modules wired into Angular frontends.
<sub>`.NET` · `Angular` · `PostgreSQL` · `Docker`</sub>

▸ **Scheduling correctness** — enforced appointment scheduling with SQL constraints and state machines, eliminating double-bookings.
<sub>`.NET Framework MVC` · `MS SQL`</sub>

▸ **Workflow-first build** — mapped the real process with sales, ops, lab, product, and UI/UX teams before writing code, then delivered the site end-to-end.

### `04` &nbsp; How I work

- Depth first — a system nobody can debug is worse than one that ships late.
- Boundaries before features, because scope changes shouldn't cause rework.
- The workflow comes first; the schema and the screen both serve it.
- Performance is a feature. So is an interface that doesn't need explaining.
- If a tool doesn't survive a team's real workflow, it's a demo, not a tool.
- Five years across credit, ERP, healthcare, and consumer products — same standard every time.
